# API03 Broken Object Property Level Authorization /n
## **BOPLA:** _Access or change unauthorized fields._ /n
BOPLA happens when a user can access or modify object properties that they are not authorized to access or change.

### Impacts
BOPLA → Unauthorized access/modification of sensitive fields
1. Read sensitive fields.
2. Modify restricted fields such as role or account status.
3. Data manipulation or privilege escalation.

### How to Test 
I test for Broken Object Property Level Authorization, or BOPLA, by checking whether a user can access or modify object properties that they are not authorized to access or change.

```
PATCH /api/users/123
Authorization: Bearer <User-A-token>
Content-Type: application/json

{
  "name": "John",
  "email": "john@example.com",
  "isAdmin": true
}
```

I would test whether sensitive properties such as `isAdmin`, `role`, `balance`, or `userId` can be **read or modified** even though the normal UI doesn't expose them.

I specifically test:

- **Excessive data exposure** → Does the API return sensitive properties the user shouldn't see?
- **Mass assignment** → Can I add unauthorized properties to a request and have the server accept them?
- **Read authorization** → Can I retrieve restricted fields?
- **Write authorization** → Can I modify restricted fields?

**Key distinction:**

- **BOLA** → unauthorized access to the **object**.
- **BOPLA** → unauthorized access to a **property/field inside the object**.

I test BOPLA by identifying sensitive object properties and then checking whether a low-privileged user can read or modify those properties through API requests, even when the application doesn't expose them through the normal interface.


### How to Prevent 
BOPLA → Property authorization
1. Allow users to access only **authorized properties/fields**.
2. Use allowlists for fields that can be modified.
3. Don't expose sensitive properties unnecessarily in API responses
