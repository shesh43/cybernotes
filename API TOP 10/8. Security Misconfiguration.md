**Misconfiguration:** _Use an insecure application/server configuration._
Security misconfiguration happens when the application or server is configured insecurely, exposing unnecessary functionality or sensitive information.

#### Impacts 
Misconfiguration → Information disclosure/system compromise
1. Sensitive information disclosure.
2. Increased attack surface.
3. Possible unauthorized access or system compromise.


#### How to Test
I test for security misconfiguration by reviewing the application's configuration, server behavior, and exposed services to identify insecure or unnecessary settings that could increase the attack surface.

I would check:

- **Default credentials** or default accounts
- Unnecessary **services, ports, and endpoints**
- **Directory listing** and exposed files
- Detailed **error messages/stack traces**
- Missing or weak **security headers**
- Incorrect **CORS configuration**
- HTTP methods that shouldn't be enabled
- **Debug/development mode** enabled in production
- Outdated or improperly configured server/framework components
- Exposed configuration files, backups, or sensitive information
- Incorrect **TLS/HTTPS** configuration
- Excessive permissions

For example, if a production application returns:
```
DatabaseException:
MySQL connection failed...
/var/www/app/config/database.php
```
that reveals internal implementation details and may indicate a **security misconfiguration**.

I identify insecure defaults, unnecessary services, excessive information disclosure, weak security controls, and improper production configurations, then verify whether they can expose sensitive information or increase the application's attack surface.


#### How to prevent 
Misconfiguration → Secure configuration
1. Remove default accounts, unnecessary services, and debug settings.
2. Apply secure server/framework configurations.
3. Regularly review configurations and security headers.
