***BOLA:** _Access another user's object._*
BOLA happens when a user can access or modify another user's object by changing the object ID.

#### Impacts
**BOLA → Unauthorized access to other users' objects**
1. Access another user's data.
2. Modify or delete another user's data.
3. Account/data privacy breach.

#### How to test :
**BOLA (Broken Object Level Authorization)** is tested by checking whether I can access or modify another user’s object by changing an object identifier.

“I test BOLA by first identifying API endpoints that use object IDs, such as `/api/users/123/orders/456`. I perform the request as User A, then change the object ID to an object belonging to User B while keeping User A’s authentication token. If the server returns or allows modification of User B’s object, that indicates a BOLA vulnerability. I also test different HTTP methods like GET, PUT, PATCH, and DELETE, because authorization must be enforced for every operation.”

```
GET /api/orders/1001
Authorization: Bearer <User-A-token>
```
If `1001` belongs to User A, that's expected.

then :
```
GET /api/orders/1002
Authorization: Bearer <User-A-token>

```
If `1002` belongs to User B and the server still returns the order → **BOLA**.

The key point is: **change the object ID, not the authentication identity, and verify whether server-side authorization is enforced.**

#### How to prevent 
1. Enforce **object-level authorization** on every request.
2. Verify the object belongs to the authenticated user
3. Never rely only on object IDs being difficult to guess.
