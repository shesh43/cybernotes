**SSRF:** _Make the server request unauthorized resources._
SSRF happens when an attacker can make the server send requests to internal or unauthorized resources.

#### Impacts 
SSRF → Access to internal resources
1. Access internal services.
2. Access sensitive internal/cloud resources.
3. Potential further compromise of internal systems.

#### How to Test
I test for SSRF by identifying API parameters that make the server fetch a URL, such as URL imports, webhooks, image fetchers, PDF generators, or URL preview functionality. I then provide a controlled URL that I own and verify whether the server makes the outbound request.

Then I test whether the server can be induced to access **internal or restricted destinations**, within an authorized test environment.

example :
```
POST /api/fetch
Content-Type: application/json

{
  "url": "https://my-controlled-domain.example/test"
}
```
If my server receives the request, I know the application is making server-side requests based on my input.

I would then assess:

- Can it reach **internal services** that shouldn't be externally accessible?
- Are requests restricted to approved destinations?
- Can redirects bypass URL validation?
- Does the application properly validate **scheme, hostname, port, and IP address**?
- Can it access cloud metadata endpoints in a permitted test environment?
- Does the server restrict outbound network access?

**Key distinction:**

In SSRF, **the attacker controls the destination of a request, but the vulnerable server makes the request on the attacker's behalf.**


I identify server-side URL-fetching functionality, use a controlled endpoint to confirm server-side fetching, and then test whether insufficient validation allows the server to reach internal or otherwise unauthorized resources.


#### how to Prevent 
SSRF → Control where the server can connect
1. Use an **allowlist of permitted destinations**.
2. Validate URLs, schemes, IPs, ports, and redirects.
3. Restrict outbound network access from the server.
